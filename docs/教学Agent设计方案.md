# 教学 Agent 设计方案

## 一、项目目标：构建一个以学习者知识模型为核心的教学 Agent

建议将这个项目设计成一个**以学习者知识模型为核心、以 PDF
为知识来源、以自适应教学为执行过程的教学 Agent**。

它不是简单的"上传 PDF → RAG 检索 →
大模型回答"，而是一个能够持续了解学习者、判断掌握程度、规划下一步教学，并根据学习结果不断更新知识模型的系统。

建议采用以下分工：

-   **Agent**：负责教学决策，确定下一步采取什么教学动作。
-   **LLM**：负责理解自然语言、解释知识、生成问题、分析学习反馈。
-   **确定性 Python 代码**：负责解析
    PDF、验证数据、执行评分规则、更新状态、管理学习流程。
-   **数据库**：负责保存教材结构、学习者模型、教学历史以及可恢复的会话状态。

核心原则：**知识模型不能只是 Agent
的一段提示词，而必须是可查询、可更新、可验证的结构化数据。**

同样，Agent 不能仅凭用户说一句"我懂了"，就认定用户已经掌握某个知识点。

## 二、核心能力

### 1. 理解教材

上传 PDF
后，提取章节、知识点、概念定义、示例、公式以及知识点之间的依赖关系，并保留原文页码作为依据。

### 2. 根据目标规划教学

用户可以指定某一章，也可以直接提出一个知识点。Agent
判断学习这个内容需要什么前置知识，再决定从哪里开始教。

### 3. 通过对话诊断知识边界

不直接假设用户什么都不懂，也不假设用户已经掌握基础。先通过有针对性的问题判断用户会什么、不会什么、哪些内容理解得不牢。

### 4. 持续维护个人知识模型

记录用户对每个知识点的掌握证据、薄弱环节、常见错误、学习历史和复习需求，而不是只保存一份聊天记录。

### 5. 根据学习效果调整教学

如果用户已经理解某个概念，就跳过重复讲解；如果用户只会背定义但不会应用，就换一个例子、补充前置知识，再进行验证。

## 三、整体架构

整体可以划分为五层。

### 1. 用户交互层

负责：

-   选择教材和章节
-   指定知识点或学习目标
-   回答诊断题和练习题
-   请求提示或更换讲解方式
-   查看学习进度与知识掌握情况

### 2. Teaching Agent

负责：

-   理解学习目标
-   诊断现有基础
-   制订教学计划
-   选择教学动作
-   判断是否继续、补课、复习或结束

可以使用 `smolagents` 实现 Agent Loop。

### 3. 教材知识服务

负责：

-   章节树和知识点查询
-   知识点前置依赖查询
-   教材原文检索
-   页码和来源引用
-   知识点学习目标与评估标准管理

### 4. 学习者模型服务

负责：

-   知识掌握状态
-   能力证据
-   常见错误与误解
-   学习偏好
-   复习需求与历史学习记录

### 5. 教学、评估与持久化服务

负责：

-   生成讲解和练习
-   分析用户回答
-   更新掌握状态
-   保存会话状态
-   调度复习任务

### 6. 底层基础设施

建议初期采用：

-   PDF 解析工具
-   SQLite
-   本地文件存储
-   LLM API 或本地模型
-   可选的全文检索或向量检索

**关键分工：LLM 负责提出教学建议，普通 Python
代码负责执行状态更新和数据校验，数据库负责持久化。**

不要让 LLM 自己决定所有数据库更新，也不要让 Agent 每次都从头阅读整本 PDF
和全部历史对话。

## 四、核心设计一：把 PDF 转换成教材知识模型

传统 RAG 通常把 PDF
切成文本块，建立索引，然后根据用户问题检索相关内容。但教学场景还需要知道：

-   这段内容属于哪一章？
-   它解释了什么知识点？
-   理解它需要哪些前置知识？
-   学完后应该具备什么能力？
-   用什么问题才能判断用户是否真正理解？

因此，建议同时构建**教材原文索引和结构化知识模型**。

### 4.1 PDF 处理流程

1.  上传 PDF。
2.  解析文本、目录、标题、页码、公式和图片。
3.  构建章节树与原文片段索引。
4.  提取原子知识点、学习目标和前置依赖。
5.  校验知识结构，建立可检索的教材知识库。

关键点是：**知识点的粒度要足够细，能够独立教学和测试。**

例如，一本讲解分布式系统的教材中，某一章讨论
Spark。不建议只创建一个"Spark"知识点，而应该拆成：

-   Spark 的整体架构
-   Driver 的职责
-   Executor 的职责
-   Job、Stage、Task 的关系
-   Shuffle 的发生条件
-   窄依赖与宽依赖的区别
-   如何根据 DAG 分析执行过程

每个知识点都可以单独诊断、讲解、练习和记录掌握情况。

### 4.2 知识点的数据结构

可以用 Pydantic 定义结构，再持久化到 SQLite。

``` json
{
  "id": "spark.shuffle",
  "title": "Shuffle 的工作机制",
  "chapter_id": "chapter_05",
  "description": "理解跨分区数据重新分布的原因与过程",
  "learning_objectives": [
    "解释 Shuffle 为什么发生",
    "区分窄依赖与宽依赖",
    "分析一个操作是否可能引起 Shuffle"
  ],
  "prerequisites": [
    "spark.rdd",
    "spark.partition",
    "spark.dependency"
  ],
  "source_refs": [
    {
      "page": 86,
      "section": "5.2",
      "chunk_id": "chunk_0086_03"
    }
  ],
  "difficulty": 3,
  "status": "verified"
}
```

字段说明：

-   `id`：稳定的知识点 ID。
-   `chapter_id`：所属章节。
-   `learning_objectives`：可被测试的问题或能力目标。
-   `prerequisites`：前置知识点 ID。
-   `source_refs`：回到教材原文的引用信息。
-   `status`：知识点结构的校验状态。

知识点 ID 应该稳定。后续即使重新解析 PDF、增加例子，也不应该轻易改变已有
ID，否则历史掌握记录会失去对应关系。

### 4.3 知识结构校验

不要完全相信模型提取的知识结构。模型可能遗漏知识点、错误识别章节、把一个概念拆得过细，或者错误判断前置依赖。

建议增加以下校验机制：

1.  检查每个知识点是否有对应的原文证据。
2.  检查前置依赖是否存在，是否出现循环依赖。
3.  检查学习目标是否可以通过问题验证。
4.  对复杂公式、图表、扫描版 PDF，支持人工确认或重新解析。
5.  将知识点标记为待校验、已确认或存在疑问。

初期不需要追求完美的知识图谱。只要能稳定地支持章节导航、知识点定位和教学顺序规划，就可以开始教学。

## 五、核心设计二：构建学习者知识模型

学习者知识模型是整个系统最有价值、也最需要精心设计的部分。

不建议把用户知识模型设计成一个简单分数，例如：

``` json
{
  "spark.shuffle": 0.8
}
```

单一分数无法说明用户为什么得分高、是否只会背定义、是否存在误解，以及模型对这个判断有多大把握。

建议将学习者模型拆成四个部分。

### 5.1 知识掌握状态

记录每个知识点的：

-   当前掌握程度
-   不同能力维度的掌握情况
-   置信度
-   最近验证时间
-   复习需求

它回答的问题是：**这个人现在会到什么程度？**

### 5.2 能力证据与错误模式

保存：

-   用户回答原文
-   题目类型
-   评分理由
-   错误类型
-   是否能解释、迁移和应用

它回答的问题是：**为什么认为他会或不会？具体卡在哪里？**

### 5.3 前置知识与薄弱环节

识别多个知识点之间的关联。例如，不理解 Shuffle，可能并不是 Shuffle
本身的问题，而是分区或依赖关系没有理解。

它回答的问题是：**问题来自哪里？应该补什么？**

### 5.4 教学偏好与学习历史

记录：

-   用户偏好的讲解方式
-   合适的难度
-   常用示例
-   学习进度
-   提示次数
-   历史教学效果

它回答的问题是：**怎样教这个人更有效？**

### 5.5 知识点掌握状态示例

``` json
{
  "user_id": "learner_001",
  "knowledge_point_id": "spark.shuffle",
  "mastery": {
    "definition": 0.9,
    "mechanism": 0.6,
    "application": 0.3,
    "transfer": 0.2
  },
  "confidence": 0.72,
  "evidence_count": 5,
  "misconceptions": [
    {
      "type": "confuses_shuffle_with_sort",
      "status": "suspected"
    }
  ],
  "last_assessed_at": "2026-10-14",
  "next_review": "pending"
}
```

这里的分数只是示例，并不是已经验证过的真实概率。

这个模型可以表达一个重要情况：用户可能能准确说出 Shuffle
的定义，却无法分析具体代码为什么发生 Shuffle。此时 Agent
不应该再次从头讲定义，而应该把教学重点放在机制、代码分析和应用上。

### 5.6 掌握度如何计算

第一版不必急于使用复杂的机器学习算法，可以从规则评分开始。

建议分别评估以下维度：

  评估维度   需要判断的问题
  ---------- ------------------------------------
  概念理解   是否理解核心概念，而非只复述术语？
  原理解释   是否能够解释为什么？
  实际应用   是否能独立解决一个问题？
  知识迁移   换一个场景后，是否仍然能够应用？
  独立程度   是否依赖提示、答案或示例？

每次评估都应该保留证据，而不是只记录总分。

可以采用以下初始规则：

-   首次正确回答定义题：增加概念理解的证据。
-   独立解释原理：增加原理理解的证据。
-   独立完成新场景题：增加应用能力的证据。
-   提示后才答对：记录为辅助完成，而不是独立掌握。
-   回答正确但理由错误：标记为需要进一步验证。
-   多次在同一错误模式上失败：建立或提高该误解的可信度。

**不要把一次答对直接等同于掌握，也不要把一次答错直接等同于不会。**

实现上，可以分别存储"当前掌握估计"和"支持这个估计的证据"。掌握度更新由
Python 中的确定性规则执行，LLM
提供结构化的评估结果，必要时再由规则层进行校验。

后续可以研究 BKT（贝叶斯知识追踪）或 IRT（项目反应理论），但它们不是 MVP
的前置条件。

## 六、核心设计三：将教学设计成持续循环

教学 Agent
与普通问答机器人的最大区别，是教学过程不是一次回答，而是一个持续循环。

### 6.1 完整教学循环

1.  **确定教学目标**：用户指定章节、知识点或学习任务。
2.  **分析前置知识与现有掌握状态**：查询教材知识模型和学习者模型。
3.  **诊断提问**：选择能够区分不同理解水平的问题。
4.  **分析回答并选择教学动作**：跳过已掌握内容、补基础、纠错或进入新知识。
5.  **讲解、示例、练习**：根据用户当前的知识边界调整深度和难度。
6.  **验证并更新知识模型**：保存回答证据，更新掌握状态和下一步计划。

未掌握时，换方法、补前置知识后再次验证；已掌握时，进入下一个知识点。

关键设计是：**Agent 每轮都要做教学决策，而不是每轮都讲一段话。**

### 6.2 教学动作设计

建议将教学动作定义为结构化枚举：

-   `ASK_DIAGNOSTIC`：提出诊断问题。
-   `EXPLAIN`：解释一个知识点。
-   `GIVE_EXAMPLE`：通过示例辅助理解。
-   `ASK_PRACTICE`：给出练习题。
-   `GIVE_HINT`：只提供部分提示。
-   `REMEDIATE`：补充前置知识或纠正误解。
-   `REASSESS`：更换题目验证掌握情况。
-   `ADVANCE`：进入下一个知识点。
-   `SUMMARIZE`：总结本次学习。
-   `REVIEW`：复习之前学习过的内容。

这些动作可以作为结构化枚举，由程序执行。LLM
负责建议下一步，程序负责校验状态、执行动作和持久化。

### 6.3 如何通过提问确定知识边界

不要只问"你懂不懂"，也不要每次都随机生成一道题。

建议采用由浅入深的诊断策略。

#### L1：概念识别

例如："你知道 Shuffle 是什么吗？"

判断用户是否接触过概念，能否识别基本术语。

#### L2：原理解释

例如："为什么某些 Spark 操作需要重新分布数据？"

判断用户是否理解机制，而非只会背定义。

#### L3：实际应用

例如："给你一段包含 `groupByKey`
的代码，你预计执行过程中会发生什么？为什么？"

判断用户能否把知识应用到具体情境。

#### L4：迁移与边界

例如："如果数据已经按目标键分区，执行计划可能有什么不同？还需要考虑什么条件？"

判断用户是否能处理变化的场景，以及是否知道结论成立的前提。

实际教学时不必每次走完四个层级。如果用户连基本概念都不了解，就先讲基础；如果已经能独立解释原理，可以直接进入应用题。

每道诊断题都应有明确目的：区分哪些可能的知识状态。

### 6.4 根据回答决定下一步

可以让 LLM 输出结构化评估，例如：

``` json
{
  "knowledge_point_id": "spark.shuffle",
  "assessment": {
    "concept_understanding": 0.9,
    "mechanism_understanding": 0.4,
    "application": 0.2
  },
  "evidence": [
    "能够说出 Shuffle 的基本定义",
    "无法解释跨分区数据交换的原因"
  ],
  "suspected_misconceptions": [
    "将 Shuffle 与排序操作混为一谈"
  ],
  "recommended_action": "REMEDIATE",
  "reason": "机制理解不足，暂时不适合进入复杂应用题"
}
```

程序拿到结果后，需要检查知识点
ID、字段范围、动作是否合法，再执行状态更新。这个 JSON
只是建议结构，不应被直接视为客观真相。

如果评分结果与用户回答之间存在明显矛盾，或者模型判断置信度不足，可以再提出一个更有区分度的问题。

## 七、核心设计四：让 Agent 利用过去的学习记录

知识模型建立之后，还必须把它接入每一次教学计划。否则即使数据库记录了所有学习结果，Agent
也可能每次重新开始教学。

建议每次教学前生成一份**个性化教学上下文**，只包含本次任务需要的信息。

例如，用户要求："教我 Spark 的 Shuffle，结合教材讲解。"

系统查询后，提供以下上下文：

``` json
{
  "learning_goal": "spark.shuffle",
  "prerequisites": {
    "spark.partition": {
      "mastery": 0.9,
      "evidence": "能够解释分区的作用"
    },
    "spark.dependency": {
      "mastery": 0.45,
      "weakness": "无法稳定区分窄依赖和宽依赖"
    }
  },
  "target_knowledge": {
    "spark.shuffle": {
      "definition": 0.8,
      "mechanism": 0.5,
      "application": 0.2
    }
  },
  "teaching_policy": {
    "skip_mastered_basics": true,
    "focus": ["dependency", "mechanism", "application"],
    "ask_before_explaining": true
  }
}
```

Agent 应据此规划：

1.  不再花大量时间讲解分区的基本定义。
2.  先用一道问题检查窄依赖和宽依赖。
3.  如果依赖关系理解不牢，先补这个前置知识。
4.  再讲 Shuffle 的发生机制。
5.  用新的代码场景测试是否真正理解。
6.  将新的回答证据写入学习者模型。

### 7.1 区分三种记忆

  记忆类型     保存什么                                   生命周期
  ------------ ------------------------------------------ ----------------
  会话状态     当前知识点、正在回答的问题、当前教学动作   当前教学会话
  学习者模型   掌握状态、错误模式、偏好、能力证据         长期
  教材记忆     章节、知识点、原文引用、依赖关系           随教材版本维护

这三者不应该混为一谈。

例如，当前会话中用户刚刚答错一道题，不代表这个错误应该永久成为用户的能力标签；但如果多次在不同题目中出现同一种错误，就值得形成长期记录。

### 7.2 遗忘与重新验证机制

人会遗忘，早期评估也可能不准确。因此，系统不能把掌握状态设置成永久不变的
`completed=true`。应该保留掌握证据的时间、独立程度和后续验证结果。

建议规则：

-   长期未复习的知识点，降低其掌握状态的置信度。
-   对重要前置知识，定期通过短题重新验证。
-   复习答对后，增强当前掌握状态的证据。
-   复习答错后，重新判断是遗忘、理解偏差还是题目本身有歧义。
-   已经稳定掌握的基础知识，降低复习频率，而不是永远重复讲解。

还要区分两个概念：**掌握度下降**和**对掌握度判断的置信度下降**。初期可以先实现后者，不必急于模拟精确的遗忘曲线。

## 八、基于 smolagents 的 Agent 与工具设计

建议第一版使用 `smolagents`，但不要把整个系统都写成一个大 Agent。

更合理的是一个负责教学决策的主 Agent，配合若干职责明确的工具。

### 8.1 工具划分

  ---------------------------------------------------------------------------------------
  工具                       职责                                 实现建议
  -------------------------- ------------------------------------ -----------------------
  `search_knowledge`         查询知识点及前置依赖                 普通 Python

  `get_source_context`       获取教材原文、页码及相关示例         普通 Python

  `get_learner_state`        获取当前知识点的掌握状态和证据       普通 Python

  `generate_diagnostic`      生成诊断题和评估标准                 LLM 辅助

  `evaluate_answer`          分析回答、识别误解、输出结构化评估   LLM 辅助

  `update_mastery`           更新学习者模型、保存评估证据         普通 Python

  `build_learning_plan`      根据目标和现有掌握情况规划学习顺序   规则为主，LLM 辅助

  `record_teaching_action`   记录讲解、提示、练习等教学行为       普通 Python

  `get_review_queue`         查询需要复习的知识点                 普通 Python

  `save_session_state`       保存会话状态，支持中断恢复           普通 Python
  ---------------------------------------------------------------------------------------

这里有一个值得坚持的原则：**LLM
决定教学策略，但程序掌握数据写入权和状态转换权。**

例如，`evaluate_answer` 返回"建议将知识点掌握度提高到 0.9"，不应该让
Agent 直接执行任意
SQL。更好的做法是让评估工具输出证据，由独立的状态更新模块按照固定规则计算新的掌握状态。

同样，不建议在第一版中就拆成多个互相对话的 Agent。单 Agent
加工具调用更容易调试、追踪错误和验证教学质量。

### 8.2 主 Agent 每轮的执行流程

1.  读取当前会话状态。
2.  查询目标知识点及其教材依据。
3.  查询相关前置知识和学习者模型。
4.  根据当前状态选择一个教学动作。
5.  调用相应工具，生成讲解或问题。
6.  等待用户回答。
7.  评估回答并保存证据。
8.  更新学习者模型和会话状态。
9.  判断继续教学、补基础、复习还是结束。

这既可以利用 `smolagents` 的 Agent
Loop，又不会把所有业务逻辑都寄托在模型的自由推理上。

## 九、数据库设计

第一版使用 SQLite
足够，不需要一开始就引入图数据库、向量数据库和复杂的分布式服务。

建议从以下几张核心表开始：

  ------------------------------------------------------------------------------------------------
  表名                                主要职责
  ----------------------------------- ------------------------------------------------------------
  `documents`                         PDF 元信息、文件哈希、版本、解析状态

  `chapters`                          章节树、父子关系、页码范围、章节顺序

  `knowledge_points`                  知识点定义、学习目标、难度、教材引用、校验状态

  `knowledge_edges`                   前置依赖、相关知识、包含关系及关系来源

  `learner_mastery`                   每个知识点的掌握估计、能力维度、置信度、最近验证时间

  `assessment_records`                题目、用户原始回答、评分、评估依据、提示使用情况、错误分类

  `teaching_sessions`                 教学目标、当前知识点、会话状态

  `session_events`                    教学动作和可恢复的事件记录

  `review_schedule`                   待复习知识点、下次复习时间、复习结果、复习间隔
  ------------------------------------------------------------------------------------------------

`learner_mastery` 保存当前状态，`assessment_records`
保存历史证据。这种设计能让你随时重新计算掌握状态，也能解释为什么 Agent
认为你已经掌握某个知识点。

向量数据库不是必须的。初期可以先通过知识点 ID、章节和 SQLite
的全文检索定位内容；当教材数量增加、跨章节语义检索确实成为瓶颈时，再加入向量检索。

## 十、教学计划生成

用户可能以两种方式发起学习：

-   **章节模式**："教我第五章。"
-   **知识点模式**："解释一下为什么 Spark 会发生 Shuffle。"

两种模式可以共用同一套规划器。

### 10.1 章节模式

1.  解析章节的知识点及学习目标。
2.  查询这些知识点的前置依赖。
3.  结合学习者模型，跳过已经有充分证据证明掌握的内容。
4.  按照依赖关系生成学习顺序。
5.  逐个教学，并根据评估结果动态调整后续计划。

### 10.2 知识点模式

1.  从教材中定位对应知识点。
2.  查询其直接前置知识。
3.  诊断用户的现有掌握情况。
4.  只补充真正需要的前置知识。
5.  完成目标知识点的教学和验证。

规划器可以先生成一个初始计划，但计划不是固定的。例如，原计划用 20
分钟学习一个知识点，如果诊断发现用户缺乏前置知识，就先补基础；如果用户已经能够独立应用，就直接进入更复杂的问题。

**建议采用"短计划 + 每轮重新规划"，而不是一次生成几十步的长计划。**

这样更适合互动式教学，因为后续教学路线取决于用户实际回答，而不是 Agent
开始时的猜测。

## 十一、项目实施阶段

建议将第一版控制在一个单用户、本地运行、支持一个文本型 PDF 的 CLI
项目。先证明自适应教学和学习者模型有效，再开发 Web 界面和更复杂的能力。

### V0--V1：教材解析与知识点管理

-   读取 PDF，提取章节、页码和文本。
-   建立知识点、学习目标和原文引用。
-   支持按章节或关键词查询知识点。

**验收标准：**能够从指定章节定位知识点，并回到原文核对。

### V2--V3：最小教学循环

-   指定知识点后，生成诊断问题。
-   分析回答、讲解、练习、纠错。
-   支持多轮交互和基础状态机。

**验收标准：**能根据回答选择继续讲解或提出下一道题，而非只生成一次性答案。

### V4--V5：学习者模型与持久化

-   记录评估证据和知识掌握状态。
-   支持中断恢复。
-   再次学习时读取历史记录。

**验收标准：**重启程序后，Agent
仍能区分已经掌握和仍需学习的知识点，并说明判断依据。

### V6--V7：自适应教学与知识依赖

-   识别前置知识缺口。
-   根据不同能力维度调整教学深度。
-   建立错误模式、复习队列和重新验证机制。

**验收标准：**相同的教学目标，对掌握水平不同的用户生成不同的学习路径。

### V8--V9：可靠性与评估体系

-   结构化输出校验。
-   防止错误评分污染知识模型。
-   建立固定测试集，评估讲解、诊断和自适应决策。

**验收标准：**同一批测试案例可以重复运行，比较修改前后的教学效果。

### V10+：扩展能力

-   Web UI、多教材和多课程管理。
-   图表、公式和扫描 PDF。
-   间隔复习、学习报告。
-   根据真实学习效果优化教学策略。

**验收标准：**不只是能运行，而是能通过学习数据持续改善教学质量。

## 十二、如何验证它真的在教会用户

这部分应该从第一版就开始设计，否则容易陷入一种假象：Agent
的回答越来越流畅，但用户的实际掌握程度没有提高。

至少准备以下几类测试：

  测试场景                 期望行为
  ------------------------ ----------------------------------------
  用户已经掌握基础         减少重复讲解，进入更高层级
  用户只会背定义           进一步验证原理和应用
  用户回答错误             识别错误原因，必要时补充前置知识
  用户在提示后答对         记录为辅助完成，后续独立验证
  用户更换一个应用场景     检查能否迁移，而不是只记住原题
  用户隔一段时间再次学习   查询历史模型，适当复习
  教材没有相关内容         明确区分教材依据与补充解释，不编造原文
  LLM 返回非法评估数据     拒绝更新，或进入重新评估流程

评估分为两个层面：

### Agent 质量

-   知识点引用准确率
-   评分合理性
-   教学动作选择准确性
-   知识模型更新正确性

### 学习效果

-   独立答题正确率
-   解释能力
-   应用能力
-   延迟复测表现
-   相较于教学前的能力提升

如果以后希望进一步研究自适应教学算法，可以固定一批教材和学习案例，比较不同教学策略的结果。但在没有足够真实学习数据之前，不建议一开始就训练自己的教学策略模型。

## 十三、推荐的第一版技术方案

  技术                    用途
  ----------------------- ------------------------------------------------
  Python + `smolagents`   Agent Loop、工具调用、教学决策
  PyMuPDF                 PDF 文本提取、页码定位和基础解析
  Pydantic                定义知识点、评估结果、教学动作等数据契约
  SQLite                  教材结构、学习者模型、历史证据和会话持久化
  pytest                  验证状态转换、评分规则、知识模型更新和回归测试

第一版不必使用多 Agent，不必一开始就上向量数据库，也不必训练自己的模型。

先把以下闭环做扎实：

**PDF → 知识点 → 诊断 → 教学 → 评估 → 学习者模型更新 →
下一次个性化教学。**

如果这个闭环有效，后续增加 RAG、复杂知识图谱、Web
界面和更先进的掌握度算法才有实际价值。

## 十四、最值得投入设计精力的三个模块

### 1. 知识点建模

如何把教材转化为可教学、可评估、有依赖关系的知识单元。

### 2. 学习者建模

如何根据回答证据判断用户会什么、不会什么，以及判断有多可靠。

### 3. 教学策略

在每个时刻，如何选择最有助于用户真正理解和掌握知识的下一步动作。

这三部分共同决定了它究竟是一个会聊天的 PDF
助手，还是一个真正能够长期陪伴用户学习的教学 Agent。
