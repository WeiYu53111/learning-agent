# 教学 Agent 三个核心模块的设计方案

这三个模块是整个教学 Agent
的核心。如果设计得好，即使底层使用的是一个普通的 8B
模型，也能通过结构化知识、可靠的学习记录和合理的教学流程，获得比单纯使用大模型问答更好的教学体验。

结合使用 Python 和 `smolagents`
从头实现这个项目的计划，建议把三个模块设计成相互协作、但职责独立的系统：

1.  **知识点建模（Knowledge
    Modeling）**：教材里有什么知识？知识之间有什么关系？怎样证明一个知识点已经被完整地理解？
2.  **学习者建模（Learner
    Modeling）**：用户掌握了什么？掌握到什么程度？判断的依据是什么？还有哪些薄弱环节？
3.  **教学策略（Teaching
    Policy）**：当前最应该教什么？应该讲解、提问、举例还是纠错？什么时候应该继续，什么时候应该复习？

三者之间形成一个持续循环：

**知识点建模提供教学目标 → 学习者建模提供用户状态 →
教学策略决定下一步行动 → 用户回答产生新的学习证据 → 学习者模型更新 →
下一轮教学重新规划。**

这不是三个互相独立的 Agent。第一版完全可以将它们实现为三个普通 Python
模块，由一个 `TeachingAgent` 统一协调，LLM
只在需要理解自然语言、生成教学内容或分析回答时参与。

# 一、核心模块一：知识点建模

## 1.1 知识点建模要解决什么问题？

假设上传了一本 Spark 教程，并要求：

> 教我 Spark Shuffle。

普通 RAG 系统可能会检索包含 Shuffle 的文本，然后让大模型生成解释。但教学
Agent 还需要回答：

-   Shuffle 在教材的哪个章节？
-   教材如何定义 Shuffle？
-   理解 Shuffle 需要掌握哪些前置知识？
-   学习 Shuffle 应该达到什么目标？
-   如何判断用户是否理解了 Shuffle？
-   如果用户不理解，应该从哪个基础知识点开始补？
-   学完 Shuffle 后，哪些后续知识点可以继续学习？

这些问题不是简单的文本检索能够完整解决的。

因此，**知识点建模的目标，是将教材从一份供模型阅读的文档，转换成一套可检索、可教学、可评估、可规划的结构化知识体系。**

建议把知识点建模拆成五个部分：

1.  教材结构建模。
2.  原子知识点建模。
3.  知识关系建模。
4.  学习目标与评估标准建模。
5.  教材证据与知识质量管理。

## 1.2 教材结构建模

首先建立教材的层级结构。例如：

``` text
Spark 教程
│
├── 第 1 章：Spark 概述
│   ├── 1.1 Spark 的设计目标
│   ├── 1.2 Spark 的整体架构
│   └── 1.3 Spark 的运行模式
│
├── 第 2 章：RDD
│   ├── 2.1 RDD 的定义
│   ├── 2.2 RDD 的分区
│   ├── 2.3 RDD 的依赖关系
│   └── 2.4 RDD 的转换操作
│
└── 第 3 章：Spark 执行机制
    ├── 3.1 Job、Stage、Task
    ├── 3.2 DAG
    └── 3.3 Shuffle
```

这只是示意结构，实际目录取决于上传的教材。

教材结构应该尽可能保留原始层级、标题、页码和顺序，不能完全依赖模型重新组织。

### 为什么需要这一层？

因为用户可能提出不同类型的学习请求：

-   教我第 3 章。
-   教我 3.2 节。
-   教我 Shuffle。
-   我不理解为什么 `groupByKey` 可能触发 Shuffle。
-   根据教材，解释 Shuffle 与 Stage 划分之间的关系。

这些请求的入口不同，但最终都需要映射到教材结构中的相关内容。

### 建议的数据结构

``` python
class Chapter:
    id: str
    document_id: str
    parent_id: str | None
    title: str
    level: int
    order: int
    start_page: int | None
    end_page: int | None
```

章节负责组织教材，不应该直接承担知识点掌握状态。

例如，用户学完了第三章中的两个知识点，不代表第三章整体已经掌握。章节完成度应该根据其学习目标和知识点状态计算，而不是手动将章节标记为已完成。

## 1.3 原子知识点建模

这是知识点建模中最重要的部分。

### 什么是原子知识点？

建议将原子知识点定义为：

**一个可以被单独解释、单独评估，并且能够明确描述其掌握标准的最小教学单元。**

例如，下面这个知识点太大：

``` text
Spark 执行机制
```

它包含太多内容，无法通过一道题判断用户是否真正掌握。可以进一步拆分为：

``` text
spark.execution.job
    Job 的概念及触发条件

spark.execution.stage
    Stage 的划分机制

spark.execution.task
    Task 与分区之间的关系

spark.execution.shuffle
    Shuffle 的作用与执行机制

spark.execution.stage_boundary
    Shuffle 与 Stage 边界的关系
```

这里的拆分不应追求知识点数量越多越好。

如果把一个知识点拆得过细，可能导致教学流程碎片化；如果拆得过粗，则无法精准诊断用户的薄弱环节。

一个实用的判断标准是：

> 如果一个知识点可以有多种明显不同的掌握状态，并且这些状态需要不同的教学策略，那么它通常值得进一步拆分。

例如，用户可能知道什么是 Stage，却不知道为什么 Shuffle Dependency 会影响
Stage 划分。这两个能力最好分别建模，否则系统无法针对性教学。

### 知识点应该包含哪些字段？

  字段                    含义              用途
  ----------------------- ----------------- --------------------------------
  `id`                    稳定的知识点 ID   关联学习记录
  `title`                 知识点名称        展示与检索
  `description`           概念描述          帮助理解知识点范围
  `chapter_id`            所属章节          章节导航
  `learning_objectives`   学习目标          判断学完后应具备什么能力
  `prerequisites`         前置知识点        规划教学顺序
  `source_refs`           教材原文引用      保证讲解有据可查
  `difficulty`            预估难度          初始教学规划
  `status`                知识点质量状态    防止未经校验的内容直接用于教学

其中，`learning_objectives` 和 `prerequisites`
特别重要，因为它们决定了知识点能否从静态的教材条目变成可以执行的教学任务。

### 知识点 ID 为什么需要稳定？

假设第一次解析教材时，系统建立了：

``` text
spark.execution.shuffle
```

你已经围绕这个知识点学习了十次，数据库中保存了大量历史证据。后来重新上传教材，解析结果把它改名为：

``` text
spark.shuffle.mechanism
```

如果系统把它当作全新的知识点，之前的学习记录就可能失去关联。

因此，知识点应该具有稳定 ID，并且将以下内容区分开：

-   知识点身份。
-   知识点内容版本。
-   教材来源版本。

教材更新时，系统可以更新知识点描述或来源，但不能随意重置历史掌握记录。

如果一个旧知识点被拆成两个新知识点，则需要显式记录迁移关系，并判断旧掌握证据是否足以支持新知识点的状态。

## 1.4 为每个知识点定义可验证的学习目标

这一部分决定了 Agent 能否真正判断用户学会了什么。

仅仅定义：

``` text
知识点：Shuffle
目标：理解 Shuffle
```

没有太大作用，因为"理解"太模糊，模型也不知道应该用什么问题验证。

建议将每个知识点的学习目标拆成若干个可以观察的能力。

例如：

### 知识点：Shuffle 的工作机制

  目标 ID   学习目标                               评估方式
  --------- -------------------------------------- ------------
  `O1`      能够解释 Shuffle 的作用                概念解释题
  `O2`      能够解释跨分区数据重新分布的原因       原理分析题
  `O3`      能够识别可能引起 Shuffle 的操作        代码分析题
  `O4`      能够分析特定执行条件下的数据交换行为   场景推理题

评估内容应该与具体教材的讲解保持一致。Spark
的实际执行行为也取决于操作类型、分区器、执行计划和版本等条件，不能将某个示例中的结论直接推广到所有场景。

### 为什么不直接给整个知识点打一个分数？

因为用户可能出现这种情况：

``` text
能够解释概念：90%
能够解释原理：80%
能够分析代码：30%
能够解决新问题：20%
```

如果只计算一个总分，例如 55%，Agent 很难知道应该怎么教。

而把学习目标拆开后，系统就能发现：

-   不需要重复讲概念。
-   需要强化原理与代码之间的联系。
-   需要安排独立应用题。
-   需要通过新场景验证迁移能力。

因此：

**知识点是组织单元，学习目标是教学和评估单元。**

一个知识点可以有多个学习目标，而学习者模型最好能够记录每个目标的掌握状态。

### 评估标准应该如何保存？

除了目标描述，还可以保存：

-   达标条件。
-   典型正确回答的要点。
-   常见错误。
-   适合的题目类型。
-   评估所需的教材依据。
-   需要排除的歧义。

这些标准不必完全由人工编写，可以由 LLM
根据教材生成初稿，再通过校验或人工审核。

对于重要知识点，建议优先建立高质量的评估标准，而不是完全依赖模型每次临时生成题目和评分规则。

## 1.5 建立知识点之间的关系

只有知识点清单，还不足以支持自适应教学。

假设用户提出：

> 我不理解 Spark 为什么会发生 Shuffle。

系统检索到 Shuffle
的定义和执行过程后，发现用户仍然无法理解。如果知识模型只有知识点清单，Agent
可能不断换一种说法解释 Shuffle。

但如果系统知道：

``` text
RDD 分区
   ↓
RDD 依赖关系
   ↓
窄依赖与宽依赖
   ↓
Shuffle 机制
   ↓
Stage 划分
```

它就有机会发现问题可能出在前置知识上。这就是知识关系建模的价值。

### 建议区分四种关系

  关系类型           示例                              作用
  ------------------ --------------------------------- --------------
  `PREREQUISITE`     理解 Shuffle 之前需要理解宽依赖   决定教学顺序
  `PART_OF`          Shuffle 机制属于 Spark 执行机制   组织知识层次
  `RELATED_TO`       Shuffle 与数据倾斜有关            提供相关知识
  `CONTRASTS_WITH`   窄依赖与宽依赖的区别              设计对比教学

`RELATED_TO`
不一定意味着前置依赖。两个知识点可能存在联系，但用户不一定需要先掌握其中一个才能学习另一个。

如果把所有关系都当作前置依赖，教学路径会变得非常冗长。

### 前置依赖关系应该怎么确定？

建议采用三种信息来源：

1.  **教材结构。** 教材可能明确说明某个概念需要先理解什么。
2.  **LLM 分析。**
    让模型根据知识点定义、学习目标和教材上下文提出前置依赖建议。
3.  **规则和人工校验。** 检查依赖是否合理，必要时由开发者或用户确认。

对于依赖关系，还可以增加置信度与来源：

``` json
{
  "source_id": "spark.dependency",
  "target_id": "spark.shuffle",
  "relation": "PREREQUISITE",
  "confidence": 0.92,
  "evidence": "理解宽依赖有助于解释 Shuffle 的数据交换机制",
  "status": "verified"
}
```

这个置信度表示系统对"该关系成立"的判断把握，并不表示某个用户对这两个知识点的掌握程度。

### 不要把知识图谱做得过于复杂

第一版使用关系表即可，不必立即使用 Neo4j。例如：

``` sql
CREATE TABLE knowledge_edges (
    source_id TEXT NOT NULL,
    target_id TEXT NOT NULL,
    relation TEXT NOT NULL,
    confidence REAL,
    status TEXT NOT NULL,
    PRIMARY KEY (source_id, target_id, relation)
);
```

字段命名需要在项目中保持一致。这里约定 `source_id`
是前置知识，`target_id`
是依赖它的后续知识。查询某个知识点的所有前置依赖后，就可以通过普通
Python 算法进行拓扑排序。

如果依赖关系出现循环，例如 A 依赖 B、B 又依赖
A，系统应将它标记为待处理，而不是无限递归。

### 区分必要前置知识和辅助知识

建议将前置关系细分为：

-   **必要前置知识：** 缺失时，用户很可能无法理解当前内容。
-   **辅助知识：** 掌握后更容易理解，但不是学习当前内容的必要条件。

这种区分可以避免 Agent
因为用户缺少一个不太重要的相关知识，就不断扩展教学范围。

## 1.6 建立教材证据系统

知识点模型不能只存储 LLM 总结出来的内容，还需要能够回到原文。

建议将教材内容分为三个层次：

  层次         内容                       用途
  ------------ -------------------------- --------------
  原始文档     PDF 文件                   保留原始依据
  原文片段     文本、页码、章节、段落     检索与引用
  知识点摘要   概念、学习目标、依赖关系   教学规划

例如：

``` json
{
  "chunk_id": "chunk_0086_03",
  "document_id": "spark_book_v1",
  "page": 86,
  "section": "3.3",
  "text": "这里保存从 PDF 提取出的原文……",
  "knowledge_point_ids": [
    "spark.execution.shuffle"
  ]
}
```

教学时，Agent 可以使用知识点摘要组织教学，再检索原文补充细节和引用。

这样做有两个好处：

1.  不需要每次都将整本 PDF 塞进模型上下文。
2.  当模型生成的解释与教材内容不一致时，可以追溯原文进行核对。

如果 PDF 包含大量图片、公式、表格或扫描页面，还需要在解析层增加
OCR、图像提取和公式处理能力。不要假设纯文本提取能够完整恢复教材内容。

### 知识点建模模块的最终输出

建议这个模块提供以下接口：

``` python
class KnowledgeService:
    def get_knowledge_point(self, knowledge_point_id):
        ...

    def search_knowledge_points(self, query):
        ...

    def get_prerequisites(self, knowledge_point_id):
        ...

    def get_learning_objectives(self, knowledge_point_id):
        ...

    def get_source_context(self, knowledge_point_id):
        ...

    def get_related_knowledge(self, knowledge_point_id):
        ...

    def validate_knowledge_graph(self):
        ...
```

这个模块只负责回答：

**教材有什么、知识之间有什么关系、学习目标是什么、依据在哪里。**

它不负责判断用户是否掌握，也不直接决定下一步如何教学。

这样可以避免知识库逻辑与 Agent 决策逻辑相互耦合。

# 二、核心模块二：学习者建模

如果说知识点建模解决的是"要学什么"，那么学习者建模解决的就是：

**当前这个人究竟会什么？我们凭什么认为他会？下一步需要补什么？**

这个模块比普通聊天记忆复杂得多。聊天记忆记录的是"说过什么"，学习者模型记录的则是"从这些交互中，有哪些关于用户能力的结论值得保留"。

## 2.1 用户状态不等于用户回答

例如，你正在学习 Python。Agent 问：

> Python 中，列表和元组有什么区别？

你回答：

> 列表可以修改，元组一般不能修改。

系统可以从这次回答中获得一些证据：

-   你知道两者的基本可变性区别。
-   你可能理解了基础概念。
-   但还没有证据证明你了解可变对象、不可变对象在实际程序中的影响。
-   也没有证据证明你能正确选择使用列表还是元组。

因此，不能直接得出"用户已经掌握列表和元组"。

更合理的做法是：

``` text
已观察到：
用户能够说出列表与元组在可变性方面的基本区别。

尚未验证：
用户是否能够解释相关行为。
用户是否能够在实际场景中正确选择数据结构。
```

**学习者模型应该记录有证据支持的能力判断，而不是把每次回答直接转化成固定标签。**

## 2.2 建立五层学习者模型

### 第一层：知识点掌握状态

记录用户对每个知识点、每个学习目标的当前掌握情况。

例如：

``` text
Python
├── 变量
│   ├── 概念理解：已掌握
│   └── 实际应用：已掌握
│
├── 列表
│   ├── 概念理解：已掌握
│   ├── 原理解释：待验证
│   └── 实际应用：部分掌握
│
└── 元组
    ├── 概念理解：已掌握
    ├── 原理解释：未验证
    └── 实际应用：未验证
```

这里的"未验证"非常重要。它不等于"不会"，只表示系统还没有足够的证据。

如果将没有学习过的知识一律标记为不会，Agent
就容易安排过多基础教学。如果将没有学习过的知识一律视为已经掌握，又容易跳过用户真正需要的内容。

因此，掌握状态至少应该区分：

-   未知：没有足够证据。
-   初步掌握：能够完成部分基础任务。
-   基本掌握：能够独立完成常见任务。
-   熟练掌握：能够解释原理并解决多种问题。
-   待重新验证：过去有掌握证据，但需要再次确认。

这些是面向用户和教学策略的状态标签，不必直接作为所有算法的计算单位。

### 第二层：能力维度

对于一个知识点，用户可能具备不同层次的能力。初期可以采用以下四个维度：

  维度            含义             典型测试
  --------------- ---------------- --------------------
  `concept`       概念识别与理解   解释定义、区分术语
  `reasoning`     原理与因果推理   解释为什么
  `application`   实际应用         解决常见问题
  `transfer`      知识迁移         解决变化后的问题

也可以额外记录
`independence`，即完成任务时对提示的依赖程度。不过，建议把独立程度作为评估证据的属性，而不是把它与前四种能力完全混在一起，因为提示依赖程度描述的是完成任务的条件，而不完全是知识本身的类型。

例如：

``` json
{
  "knowledge_point_id": "python.mutable_object",
  "mastery_by_objective": {
    "concept": 0.90,
    "reasoning": 0.65,
    "application": 0.40,
    "transfer": null
  }
}
```

这里的 `null`
表示尚未获得足够的评估证据，不代表能力为零。这些数值是示例性的掌握估计，并不是客观测量出的精确概率。

### 为什么要分维度？

假设用户在概念题中表现很好，但实际应用题经常出错。如果只有一个总体分数，Agent
可能仍然认为用户已经掌握。

而分维度之后，它就可以决定：

> 不再重复解释基本定义，改用具体代码分析和小型练习，帮助用户把概念转化为实际应用能力。

这正是学习者模型为教学策略提供价值的方式。

## 2.3 第三层：学习证据

这是整个学习者模型最值得认真设计的一层。

如果只保存掌握分数，系统无法解释分数是怎么来的。例如：

``` json
{
  "knowledge_point_id": "python.mutable_object",
  "mastery": 0.75
}
```

这个数据几乎无法帮助我们诊断问题。它没有说明用户回答过什么问题、是否使用提示、模型为什么给出这个分数、用户是否理解原理、之前是否出现过相同错误，以及最近一次评估是什么时候。

因此，建议把学习证据独立保存。例如：

``` json
{
  "assessment_id": "assessment_001",
  "knowledge_point_id": "python.mutable_object",
  "objective_id": "reasoning",
  "question": "为什么修改一个列表变量可能影响另一个变量引用的对象？",
  "answer": "因为它们可能引用同一个列表对象。",
  "hint_level": 0,
  "result": "mostly_correct",
  "evidence": [
    "能够识别两个变量可能引用同一对象",
    "尚未解释对象引用与变量赋值之间的关系"
  ],
  "error_types": [],
  "assessed_at": "2026-10-14"
}
```

这个记录可以在未来帮助 Agent 判断用户是否真正理解了相关概念。

### 学习证据应该记录哪些信息？

建议至少包含：

1.  评估的问题。
2.  用户原始回答。
3.  对应的知识点和学习目标。
4.  评估结果及理由。
5.  是否使用了提示。
6.  是否展示过标准答案。
7.  题目难度与题目类型。
8.  评估时间。
9.  评分规则或模型版本。
10. 评估结果的可靠性信息。

其中第 5、6
项尤其重要。如果用户在看到答案之后正确复述，不能把它和完全独立的回答视为相同证据。同样，如果一道题本身有歧义，也不应该因为用户答错就降低掌握度。

### 为什么要保存原始回答？

因为 LLM
的评分结果可能有错误。例如，模型第一次认为用户不理解某个概念，但后续发现原回答其实是正确的，只是表达方式与预期答案不同。

如果只保存最终分数，就很难纠正历史判断。保留原始回答后，可以重新评估证据，也可以修改评分规则，再计算新的掌握状态。

因此，建议遵循：

**原始回答不可覆盖，评估结果可以修正，当前掌握状态可以重新计算。**

## 2.4 第四层：错误模式与知识缺口

这一层用于回答：

**用户为什么学不会？问题到底出在哪里？**

例如，在学习 Spark Shuffle 时，用户连续出现以下情况：

1.  不知道宽依赖和窄依赖的区别。
2.  无法解释为什么需要跨分区交换数据。
3.  不理解 Shuffle 与 Stage 划分之间的关系。

这些错误表面上涉及三个知识点，但可能存在共同原因：对 RDD
依赖关系的理解不够牢固。

如果系统只记录每个知识点的掌握分数，就很难发现这个共同原因。因此，建议把错误模式独立建模。

例如：

``` json
{
  "pattern_id": "confuses_dependency_types",
  "description": "无法稳定区分窄依赖与宽依赖",
  "related_knowledge_points": [
    "spark.dependency",
    "spark.shuffle",
    "spark.stage_boundary"
  ],
  "status": "suspected",
  "evidence_count": 3,
  "last_observed_at": "2026-10-14"
}
```

错误模式的建立需要有足够的证据。一次答错只能作为一个候选信号。连续在多个不同场景中出现相同错误，才更有理由把它视为稳定的薄弱环节。

### 如何发现共同薄弱环节？

第一版可以采用简单规则，不需要训练专门的模型。例如：

``` text
IF
    多个相关知识点连续评估失败
AND
    这些知识点存在共同的前置依赖
THEN
    检查共同前置知识是否存在缺口
```

具体实现时，还需要考虑：

-   题目是否过难。
-   是否使用了提示。
-   用户是否误解了题意。
-   不同错误是否真的来自同一个原因。
-   相关前置知识是否已经被独立验证。

如果证据不足，系统应该提出一个诊断问题，而不是直接断言用户缺乏某项能力。

### 从错误模式到教学动作

``` text
观察到的问题：
用户反复混淆窄依赖与宽依赖。

系统检查：
用户是否掌握 RDD 分区的基本概念？

如果没有：
先补充分区知识。

如果已经掌握：
使用对比示例解释两种依赖的区别。

然后：
换一个新的执行场景，验证是否真正理解。
```

这比让 Agent 不断重新解释 Shuffle 更有效。

## 2.5 第五层：学习历史、偏好与复习状态

学习者模型不仅应该记录用户当前的能力，还需要保留足以帮助未来教学的长期信息。

但这里有一个设计原则：

**只保存能够改善教学决策的信息，不要把所有聊天内容都当作学习记忆。**

例如，可以记录：

-   用户喜欢先理解原理，再看代码。
-   用户在没有示例时难以理解抽象概念。
-   用户能够阅读 Python 代码，但对某个数学概念不熟悉。
-   用户最近学习过哪些知识点。
-   哪些知识点已经很久没有重新验证。
-   哪些知识点经常需要提示才能答对。

这些信息会直接影响下一次教学。但不必把所有闲聊、临时问题和无关个人信息都存进学习者模型。

### 学习偏好应该如何维护？

不要在第一次交互时就永久认定用户喜欢某种教学方式。可以把偏好分成两类：

-   **显式偏好：** 用户直接告诉系统，例如"请先解释原理，再给代码"。
-   **观察到的偏好：** 系统发现某种教学方式通常能让用户更好地理解。

显式偏好应该优先尊重；观察到的偏好则需要根据多次交互不断修正。

例如，用户平时喜欢详细解释，但当前只是想快速复习一个已经掌握的概念。系统不应该机械地每次都输出长篇讲解。

## 2.6 掌握度算法：第一版到底应该怎么计算？

建议分三个阶段实现。

### 阶段 A：规则评分

这是最适合 MVP 的方案。

为每个学习目标保存若干项评估证据，例如：

``` text
目标：解释列表和元组的区别

证据 1：基础概念题，独立答对
证据 2：解释可变性，回答不完整
证据 3：代码应用题，独立答对
```

然后根据题目类型、正确程度、提示依赖等因素，更新掌握估计。

  评估结果             初期处理建议
  -------------------- --------------------------------
  独立答对基础题       增加基础概念掌握证据
  独立解释原理         增加原理理解证据
  独立完成应用题       增加应用能力证据
  使用提示后答对       记录为辅助完成
  看过答案后答对       不作为独立掌握证据
  答错且暴露稳定误解   记录错误模式并安排补救
  题目存在歧义         不更新掌握状态，先处理题目问题

第一版不建议设置复杂的数学公式，因为如果评估本身不可靠，再精确的公式也只会让错误判断显得更加精确。

### 阶段 B：基于证据的概率估计

当积累了足够多的评估记录，可以进一步引入
BKT（贝叶斯知识追踪）。它试图根据连续的答题结果，估计学习者掌握某个知识点的概率。

其基本思路是区分：

-   学习者当前是否已经掌握。
-   学习者答题时是否可能猜对。
-   已经掌握的人是否仍可能答错。
-   学习过程中掌握状态发生变化的可能性。

这比简单累计正确率更合理，但需要谨慎设定参数，也需要考虑题目质量、难度和提示依赖。

### 阶段 C：引入更细致的学习者模型

未来可以考虑：

-   **BKT：** 跟踪某个知识点的掌握变化。
-   **IRT：** 考虑题目难度、区分度与学习者能力之间的关系。
-   **遗忘模型：** 估计经过一段时间后，某项知识是否需要复习。
-   **多维知识追踪：** 分别估计概念理解、推理和应用能力。

不过，不建议一开始就实现这些算法。当前最需要验证的是知识点划分是否合理、诊断问题是否有效，以及评估结果是否真的能改善教学决策。

### 不要把所有题目等权处理

一道简单的定义题和一道综合应用题，提供的能力证据不同。同样，一道题如果直接重复刚刚讲解的例子，也不如一道新场景题能够证明用户具备迁移能力。

因此，掌握状态更新至少应该考虑：

-   对应哪个学习目标。
-   题目考查什么能力。
-   是否独立完成。
-   是否依赖提示。
-   是否见过相同题目或答案。
-   评估结果是否可靠。

即使第一版采用规则评分，也应在数据模型中保留这些信息，避免未来升级算法时无法利用历史数据。

# 三、核心模块三：教学策略

前两个模块分别解决了"教材中有什么"和"用户会什么"。

教学策略要解决的是最复杂的问题：

**在当前时刻，采取什么教学动作，最有可能帮助用户理解并掌握目标知识？**

建议把教学策略拆成四个子模块：

1.  教学目标规划：决定教什么。
2.  教学动作选择：决定下一步做什么。
3.  教学内容生成：决定具体怎么讲、怎么问。
4.  教学效果评估与调整：决定是否继续、换方法或补基础。

其中，最核心的是第二个模块：教学动作选择。

## 3.1 建立教学策略的基本原则

传统问答系统的工作模式是：

``` text
用户提问
   ↓
检索相关资料
   ↓
LLM 生成答案
   ↓
返回答案
```

教学 Agent 则应该是：

``` text
用户提出学习目标
   ↓
获取知识点及其学习目标
   ↓
查询学习者模型
   ↓
判断当前处于什么教学状态
   ↓
选择下一步教学动作
   ↓
执行教学动作
   ↓
根据用户反馈更新状态
   ↓
重新决定下一步动作
```

教学策略不是提前写好一份教学大纲，然后让 Agent
从头执行到尾，而是根据学习者的实际表现动态调整计划。

例如，原计划用四步讲解一个概念，但用户在第一步就暴露出前置知识缺口，那么后续步骤就应该调整。反过来，如果用户已经能够独立解释原理，Agent
就不应该为了完成预设流程而继续重复讲解。

## 3.2 子模块一：教学目标规划

首先要决定用户当前应该学习什么。这需要综合三个信息来源：

-   用户明确提出的学习目标。
-   知识点之间的前置依赖关系。
-   学习者模型中的掌握状态。

### 场景 A：用户指定章节

例如：

> 教我第五章。

系统不能直接把第五章所有内容交给 LLM，然后一次性讲完。

建议按以下流程处理：

**第一步：提取章节学习目标。**

获取第五章包含的知识点、每个知识点的学习目标，以及它们之间的依赖关系。

**第二步：查询学习者模型。**

确定哪些知识点已经掌握、哪些尚未验证、哪些存在明确的薄弱环节。

**第三步：建立候选学习列表。**

  知识点        当前状态           初步处理
  ------------- ------------------ ----------------
  A：基础概念   已有充分掌握证据   暂时跳过
  B：核心原理   部分掌握           安排针对性教学
  C：执行机制   尚未验证           先诊断
  D：综合应用   前置知识不足       暂不进入

**第四步：按照依赖关系生成初始计划。**

``` text
1. 快速验证 B 的薄弱部分
2. 补充 B 中尚未理解的原理
3. 诊断 C 的基础
4. 教学 C
5. 使用综合应用题验证 B 和 C
```

这里的计划只是初始方案。后续每完成一个教学动作，都应该根据新证据决定是否调整。

### 场景 B：用户直接提出知识点

例如：

> 我想知道为什么 Spark 会发生 Shuffle。

此时不需要先规划整个章节。可以只围绕目标知识点构建一个局部学习计划：

1.  获取 Shuffle 的学习目标。
2.  查询必要前置知识。
3.  检查用户现有掌握证据。
4.  对缺少证据的关键前置知识进行诊断。
5.  只补充必要的知识缺口。
6.  教学目标知识点。
7.  通过新问题验证掌握情况。

**章节模式是从较大的范围向下规划，知识点模式是从目标向前检查依赖。两者可以共用同一个规划器。**

### 教学计划的数据结构

建议让规划器输出结构化计划：

``` json
{
  "goal_id": "spark.shuffle",
  "plan": [
    {
      "knowledge_point_id": "spark.dependency",
      "action": "DIAGNOSE",
      "reason": "需要确认用户是否理解依赖关系"
    },
    {
      "knowledge_point_id": "spark.shuffle",
      "action": "TEACH",
      "reason": "目标知识点"
    },
    {
      "knowledge_point_id": "spark.shuffle",
      "action": "ASSESS",
      "reason": "验证原理理解与实际应用"
    }
  ],
  "status": "active"
}
```

这里的 `action`
表示规划阶段的建议动作，并不意味着整个计划必须按原样执行。实际执行时，教学策略还需要根据用户反馈动态调整。

## 3.3 子模块二：教学动作选择

这是整个教学策略的核心。

第一版不要让 LLM
完全自由地决定下一步做什么，而是建立一个有限的教学动作集合，再让 Agent
根据当前状态选择动作。

### 定义教学动作

  动作          作用               适用场景
  ------------- ------------------ --------------------------------
  `DIAGNOSE`    诊断当前知识边界   不知道用户掌握到什么程度
  `EXPLAIN`     解释知识点         用户缺少概念或原理理解
  `EXAMPLE`     提供具体示例       抽象概念难以理解
  `PRACTICE`    安排练习           需要验证实际应用能力
  `HINT`        提供部分提示       用户遇到困难，但仍可能独立解决
  `REMEDIATE`   补救教学           发现前置知识缺口或稳定误解
  `REASSESS`    重新评估           需要验证纠错是否有效
  `ADVANCE`     进入下一个知识点   当前目标已达到预定标准
  `REVIEW`      复习旧知识         已到复习时间或发现遗忘迹象
  `SUMMARIZE`   总结本轮学习       用户准备结束本次学习

这些动作的定义应该稳定。LLM
可以推荐动作，但不能任意发明一个程序无法识别的新动作。

### 教学动作如何选择？

建议采用：

**规则负责约束和基本决策，LLM 负责处理需要理解语义的复杂情况。**

例如，可以先实现下面的规则：

``` python
def choose_teaching_action(state):
    if state.active_question is not None:
        return "WAIT_FOR_ANSWER"

    if state.has_unresolved_evaluation:
        return "EVALUATE_ANSWER"

    if state.has_confirmed_prerequisite_gap:
        return "REMEDIATE"

    if state.needs_diagnostic:
        return "DIAGNOSE"

    if state.target_is_mastered:
        return "ADVANCE"

    if state.has_active_misconception:
        return "EXPLAIN"

    if state.needs_application_practice:
        return "PRACTICE"

    return "EXPLAIN"
```

这只是展示决策结构的示意代码，实际开发时需要根据状态优先级调整条件。例如，用户答错后，不一定马上重新解释。系统可能应该先分析错误原因，判断是概念不清、题意理解错误，还是缺乏应用经验。

更合理的实现方式是先确定当前教学状态，再由策略模块选择动作。

### 为什么不能只依靠规则？

因为教学场景有很多复杂情况。

例如，用户回答：

> 我觉得 Shuffle 就是把数据排序。

这句话可能意味着：

-   用户确实把 Shuffle 与排序混淆。
-   用户只是用不严谨的语言描述数据处理过程。
-   用户理解数据重新分布，但没有表达清楚。
-   用户只了解某一种涉及排序的具体操作。

仅凭关键词匹配，很难确定问题的真正原因。

这时 LLM 可以分析回答，并给出结构化判断：

``` json
{
  "interpretation": "用户可能将 Shuffle 与排序混淆",
  "confidence": 0.78,
  "evidence": [
    "用户将 Shuffle 直接定义为排序"
  ],
  "recommended_action": "DIAGNOSE",
  "reason": "需要进一步区分概念误解与表达不准确"
}
```

策略模块可以据此提出一道有区分度的问题，而不是立即将用户标记为不理解。

这里的 `confidence`
仍然只是模型的自评信号，不能直接当作经过校准的真实概率。

## 3.4 如何设计诊断策略？

诊断不是随机出题，而是选择能够区分不同知识状态的问题。

假设系统想确认用户是否理解 Shuffle。有三个待判断的状态：

-   状态 A：不知道 Shuffle 的基本概念。
-   状态 B：知道概念，但不理解发生机制。
-   状态 C：理解机制，但无法分析具体执行场景。

如果直接问一道复杂的综合题，用户答错后，系统无法知道到底是哪一层出了问题。因此，诊断应该有明确的层次。

### 第一层：概念诊断

问题：

> 你认为 Shuffle 在分布式计算中主要解决什么问题？

如果用户无法回答，系统可能需要先讲解概念。如果回答正确，则继续判断其原理理解。

### 第二层：原理诊断

问题：

> 为什么某些操作需要把不同分区的数据重新分配？

如果用户能够解释数据重新分布的必要性，说明已经有一定的机制理解。如果只是重复定义，则还需要进一步确认。

### 第三层：应用诊断

问题：

> 给你一个具体的数据处理操作，你如何判断它是否可能触发 Shuffle？

这时考查的已经不是记忆，而是能否将原理应用到新场景。题目必须明确相关条件，否则用户可能因为题目缺少信息而给出不同但合理的答案。

### 诊断策略还可以考虑什么？

第一版建议增加以下机制：

1.  **优先检查重要前置知识。** 不要在基础不稳的情况下连续安排复杂问题。
2.  **根据回答选择下一题。** 答对后增加难度，答错后缩小问题范围。
3.  **控制诊断成本。** 不要为了确定用户是否会一个概念而连续问十几道题。
4.  **处理不确定情况。** 如果回答含糊，换一种表达或给出具体场景。
5.  **避免题目重复。** 刚刚讲过的例子不能反复用于证明用户已经独立掌握。
6.  **允许用户主动跳过。**
    用户可以要求直接讲解，但系统应保留"尚未验证"的状态。

自适应教学不是强迫用户参加考试，而是根据用户的目标和意愿调整教学方式。

## 3.5 如何决定什么时候讲解、什么时候提问？

我建议先建立简单的决策表。

  ---------------------------------------------------------------------------------
  当前状态                     推荐动作                     目的
  ---------------------------- ---------------------------- -----------------------
  用户完全不了解概念           简短讲解，再做基础检查       建立初始认知

  用户知道定义，但解释不清     通过问题定位具体误解         避免重复讲解

  用户理解原理，但不会应用     提供示例，再逐步撤除提示     建立应用能力

  用户能完成常见问题           安排变化场景的练习           检验迁移能力

  用户连续答错同一类型的问题   检查前置知识，调整讲解方式   解决根本问题

  用户已经稳定掌握             进入下一知识点或安排复习     避免无效重复

  旧知识长期未验证             安排简短复习题               检查遗忘情况
  ---------------------------------------------------------------------------------

这些规则不是最终的教学理论，而是一个可以实施、测试和持续改进的起点。

### 先确定错误类型，再选择纠错方式

例如，用户答错一道代码分析题，系统应该尝试区分：

-   概念错误：没有理解基础概念。
-   原理错误：知道概念，但不知道为什么。
-   应用错误：理解原理，却无法应用。
-   表达问题：理解正确，但表述不准确。
-   题目问题：题意不明确或条件不足。

不同错误对应不同的教学动作。如果是概念错误，就补充解释；如果是应用错误，就通过示例和练习建立联系；如果只是表达不准确，则不应该直接降低掌握度；如果是题目问题，就应该修正题目，而不是纠正用户。

这也是为什么评估模块需要输出错误类型和证据，而不仅仅是正确或错误。

## 3.6 子模块三：教学内容生成

教学策略决定了应该做什么，但具体怎么讲，仍然需要 LLM 生成内容。

建议将教学动作与内容生成分离。例如，策略模块决定：

``` text
动作：EXPLAIN
目标：解释宽依赖与窄依赖的区别
教学方式：对比示例
深度：基础原理
```

然后内容生成模块根据这个任务生成实际讲解。这样，同一个知识点可以根据不同用户状态采用不同的讲法。

### 教学内容生成需要哪些输入？

至少包括：

``` text
1. 当前教学目标
2. 目标知识点的定义和学习目标
3. 相关教材原文
4. 用户已掌握的前置知识
5. 用户当前的薄弱环节
6. 本轮教学动作
7. 用户偏好的讲解方式
8. 当前教学深度
9. 必须遵守的教材引用规则
```

其中，前置知识和薄弱环节尤其重要。假设用户已经理解了 RDD
分区，但不理解宽依赖，系统就不应该再次解释什么是分区，而应该直接围绕依赖关系讲解。

### 建议使用统一的教学任务结构

例如：

``` json
{
  "action": "EXPLAIN",
  "knowledge_point_id": "spark.dependency",
  "objective_id": "reasoning",
  "teaching_depth": "intermediate",
  "focus": [
    "窄依赖与宽依赖的区别",
    "依赖关系对执行过程的影响"
  ],
  "known_prerequisites": [
    "spark.rdd",
    "spark.partition"
  ],
  "avoid_repeating": [
    "RDD 的基础定义",
    "分区的基本概念"
  ],
  "source_refs": [
    "chunk_0086_03"
  ]
}
```

然后让 LLM
根据该结构生成讲解。这比每次只发送一句"请教我宽依赖"更容易控制教学质量。

### 教学内容应该有统一的基本结构吗？

建议有，但不要僵化。对于第一次学习某个概念，可以采用：

1.  先说明这个概念解决什么问题。
2.  用一个具体例子建立直觉。
3.  解释核心机制。
4.  指出容易混淆的概念。
5.  给出一个简单问题检查理解。
6.  根据回答决定下一步。

对于已经理解基础、正在练习应用的用户，则可以直接给出场景问题，不必重复整个流程。

也就是说，**教学模板应该由教学动作决定，而不是每次都套用同一份固定格式。**

## 3.7 子模块四：教学效果评估与动态调整

教学不是把讲解内容发给用户就结束了。系统还需要判断：

-   用户是否理解了刚刚讲解的内容？
-   之前的误解是否消失？
-   是否可以进入更高难度的任务？
-   是否需要换一种讲解方式？
-   是否应该暂停当前知识点，先补前置知识？

这里需要区分两种评估。

### 即时评估

判断用户是否理解刚刚讲解的内容。例如，讲解了窄依赖和宽依赖之后，使用一个没有在讲解中出现过的简单场景，让用户判断依赖类型并解释理由。

### 延迟评估

在之后的学习中，再次检查用户是否能够独立应用该知识点。因为用户刚刚看完解释后答对，并不能证明已经形成稳定的理解。

因此，学习者模型应该保留评估时间、提示使用情况和题目重复情况，避免将短期记忆误认为长期掌握。

### 如何判断教学已经完成？

不要简单使用：

``` python
if mastery > 0.8:
    mark_completed()
```

更合理的方式是基于学习目标和证据设置完成条件。例如，对于一个需要掌握原理和应用的知识点，可以要求：

-   核心概念理解达到标准。
-   原理解释达到标准。
-   至少完成一道独立应用题。
-   不存在尚未解决的关键误解。
-   评估证据具有足够的可靠性。

对于基础术语，则可以使用更简单的标准。完成条件应该与知识点的重要性和学习目标相匹配。

### 如果用户一直答错怎么办？

建议设置明确的停止条件，避免 Agent
不断重复讲解、不断出题，最终形成无效循环。

``` text
第一次答错：
分析错误原因，提供针对性提示。

第二次仍然答错：
更换示例，检查是否缺少前置知识。

第三次仍然答错：
降低难度，回到更基础的知识点。

如果依然无法理解：
总结当前障碍，询问用户是否希望换一种讲法或暂时跳过。
```

这里的次数只是初始策略，可以根据教学实验调整，不应当被当作普遍有效的固定规律。更重要的是，每次失败之后，教学动作应该发生有意义的变化，而不是重复相同的问题。

# 四、三个模块如何协同工作？

假设用户要求：

> 教我 Spark 的 Shuffle，我已经知道 RDD 是什么。

系统中已有如下知识点：

``` text
RDD
  ↓
RDD 分区
  ↓
RDD 依赖关系
  ↓
Shuffle
  ↓
Stage 划分
```

学习者模型记录：

``` text
RDD 概念：有充分证据表明已掌握
RDD 分区：有充分证据表明已掌握
RDD 依赖关系：尚未验证
Shuffle：尚未验证
Stage 划分：尚未验证
```

注意，"已掌握"也不代表永远不需要复习，只表示当前有足够的证据支持这个判断。

## 第一步：知识点建模模块提供信息

系统获取：

-   Shuffle 的定义。
-   Shuffle 的学习目标。
-   对应的教材原文。
-   必要的前置知识。
-   与 Stage 划分的关联。

## 第二步：学习者建模模块提供状态

系统发现：

-   RDD 和分区已有掌握证据。
-   依赖关系还没有经过验证。
-   Shuffle 尚未学习。

## 第三步：教学策略选择动作

Agent 决定先用一道问题确认用户是否理解 RDD 依赖关系，再决定是否进入
Shuffle。

于是它提出：

> 假设一个 RDD
> 的某个输出分区只依赖上游的一个分区，而另一个操作的输出分区需要读取多个上游分区的数据。你觉得这两种依赖有什么区别？

## 第四步：用户回答

假设用户回答：

> 第一种是窄依赖，第二种是宽依赖，但我不知道为什么这和 Shuffle 有关系。

## 第五步：学习者模型更新

系统记录：

-   用户能够初步区分两种依赖。
-   用户尚未解释它们与数据重新分布的关系。
-   需要进一步验证其对依赖机制的理解。

此时不能直接认定用户完全掌握依赖关系。

## 第六步：教学策略重新规划

Agent 决定：

1.  不再重复 RDD 的定义。
2.  用数据分区示例解释依赖关系。
3.  说明跨分区数据交换与 Shuffle 的关系。
4.  再用一个新的场景检验用户能否解释这一机制。

## 第七步：验证并更新

如果用户能够独立解释原理，但仍然无法分析代码，那么学习者模型可以更新为：

``` text
概念理解：基本掌握
原理理解：基本掌握
实际应用：仍需验证
```

下一步就应该进入代码分析，而不是继续重复原理讲解。

这个例子说明了三个模块之间的职责边界：

-   知识点建模告诉系统要教什么，以及它依赖什么。
-   学习者建模告诉系统用户目前掌握到什么程度。
-   教学策略决定下一步应该采取什么动作。

**三个模块之间应该通过结构化数据交换，而不是通过彼此拼接越来越长的提示词来协作。**

或不存在的教学动作所导致的问题。

# 六、哪些事情交给 LLM，哪些事情交给 Python？

这会直接影响整个系统的可靠性。

  任务               推荐实现方式      原因
  ------------------ ----------------- --------------------------
  PDF 文本提取       Python 工具       可重复执行，便于验证
  章节与页码管理     Python + 数据库   必须保持结构一致
  知识点初步提取     LLM + 校验        需要理解教材语义
  前置依赖建议       LLM + 图校验      需要推理，但结果可能出错
  查询掌握状态       Python + 数据库   必须读取真实记录
  分析自然语言回答   LLM               需要理解语义
  评估回答正确性     LLM + 规则        需要语义判断和可靠性控制
  掌握状态更新       Python            规则需要稳定、可测试
  初始教学计划       Python + LLM      兼顾约束与复杂语义
  当前教学动作选择   规则 + LLM        兼顾可控性与灵活性
  生成讲解与问题     LLM               需要自然语言生成
  保存教学历史       Python + 数据库   必须可靠持久化

最值得坚持的一条原则是：

**不要让 LLM
同时负责判断事实、决定策略、修改数据库，并且自己宣布任务完成。**

应该把这几个职责拆开。

例如，LLM 可以建议：

> 用户对依赖关系的理解不足，建议补充基础知识。

但真正是否进入补救教学，应由策略模块结合历史证据和教学状态决定。同样，LLM
可以给出对用户回答的评估，但掌握状态应该由独立的更新规则计算。

这样才能让系统可调试、可测试，也便于未来更换模型。

# 七、三个模块应该如何开发？

虽然三个模块最终需要协同工作，但不建议同时开发。

## 第一阶段：先做好知识点建模

先支持一个 PDF，完成：

-   章节解析。
-   原子知识点提取。
-   学习目标生成。
-   前置依赖关系。
-   原文引用与页码定位。
-   知识点质量校验。

**验收标准：**
用户指定一个知识点，系统能够返回知识点定义、学习目标、必要前置知识和可靠的教材引用。

这一步不需要先实现复杂 Agent。

## 第二阶段：建立最小学习者模型

完成：

-   按学习目标记录掌握状态。
-   保存题目和原始回答。
-   记录提示使用情况。
-   保存评估证据。
-   使用规则更新掌握状态。
-   支持历史记录查询。

**验收标准：**
用户答过几道题后，系统能够解释为什么认为他掌握或没有掌握某个学习目标，并能在重新启动后保留这些记录。

## 第三阶段：实现教学策略状态机

先只支持少数几种动作：

``` text
DIAGNOSE
EXPLAIN
PRACTICE
REMEDIATE
ADVANCE
```

实现：

-   初始教学计划。
-   诊断问题生成。
-   回答评估。
-   教学动作选择。
-   前置知识补救。
-   达标判断。
-   会话恢复。

**验收标准：**
对于同一个知识点，系统能够根据不同的用户回答走向不同的教学路径，而不是每次都执行相同的讲解流程。

## 第四阶段：把三个模块整合起来

这时再通过 `smolagents` 统一协调工具调用。

重点验证以下三个场景：

1.  用户已经掌握基础，Agent 能够跳过重复内容。
2.  用户不理解目标知识，Agent 能够定位前置知识缺口。
3.  用户经过教学后，Agent 能够通过新题验证理解，并更新长期知识模型。

如果这三个场景都能稳定运行，你就已经实现了教学 Agent 最核心的能力。

之后再增加间隔复习、更复杂的掌握度算法、多个 PDF、Web UI 等功能。

# 八、三个需要提前解决的难题

## 难题一：知识点划分得好不好，决定了整个系统的上限

如果一个知识点包含太多能力，学习者模型就无法准确判断用户到底会什么。

如果一个知识点过于细碎，教学策略又会产生大量不必要的步骤。

因此，需要为知识点建立明确的划分标准，并通过实际教学案例不断验证。

## 难题二：评估可靠性比掌握度公式更重要

如果 LLM 经常误判用户的回答，再复杂的掌握度算法也无法得到可靠结果。

所以第一版应该优先做好：

-   题目质量。
-   学习目标与评估标准的一致性。
-   提示依赖记录。
-   原始回答留存。
-   评估结果的可追溯性。
-   不确定情况下的再次诊断。

先提高证据质量，再研究更复杂的算法。

## 难题三：教学策略不能只看掌握度分数

假设用户在一个知识点上的掌握度只有
0.4，这并不能直接告诉我们下一步应该讲什么。

低掌握度可能来自不同原因：

-   用户根本没接触过这个概念。
-   用户记住了定义，但不理解原理。
-   用户理解原理，却缺少应用经验。
-   用户之前掌握过，但现在已经遗忘。
-   用户遇到了一道有歧义的题目。

这些情况需要不同的教学动作。

因此，教学策略应该综合考虑：

**掌握状态 + 学习目标 + 评估证据 + 错误模式 + 前置知识 +
当前会话状态。**

掌握度只是输入之一，不是唯一的决策依据。

# 九、最终建议：先实现一个可以验证的最小闭环

如果由我来设计这个项目，我会先不追求复杂的 Agent
架构，而是优先实现下面这条完整链路：

``` text
用户指定知识点
       ↓
知识点建模
获取学习目标、前置知识和教材依据
       ↓
学习者建模
读取现有掌握状态和历史证据
       ↓
教学策略
选择一个诊断问题
       ↓
用户回答
       ↓
评估回答
判断能力表现、错误类型和证据可靠性
       ↓
更新学习者模型
       ↓
教学策略重新决策
       ↓
讲解 / 提示 / 练习 / 补基础 / 进入下一知识点
       ↓
再次评估
       ↓
保存结果，等待下一轮学习
```

**只要这条链路能够稳定运行，你的教学 Agent
就已经拥有了真正的自适应教学基础。**

后续增加 RAG、知识图谱、BKT、间隔复习或多
Agent，都应该服务于这条主链路，而不是为了技术复杂度而引入。

我尤其建议在实现时坚持一个设计目标：

> 对于每一次教学动作，系统都应该能够回答三个问题：为什么现在要做这件事？依据了哪些教材和学习证据？做完之后，如何判断这一步是否有效？

如果这三个问题都能得到明确回答，这个系统就不仅是一个会解释 PDF
的助手，而是一个具备可追溯决策过程、能够持续更新学习者模型的教学系统。
